The problem

The chat is not
a plan

Drift

Each prompt nudges the result further from what you meant, and nobody wrote down what that was.

No baseline

You can't judge a diff if there is nothing to judge it against.

Lost context

Close the chat and the reasons are gone. The next agent starts from zero.

Two ways to build

Review the intent
before the code

Vibe coding

  • Prompt → code → “looks fine”
  • The chat is the record
  • You review only the result
  • Fast to start, hard to change

Spec-driven

  • Proposal → spec → tasks → code
  • The repo is the record
  • You review the intent, then the result
  • Slower to start, safe to change
It is cheaper to fix a sentence than a feature.
OpenSpec

Specs that live
in your repo

openspec/
├── config.yaml   # what the project is
├── specs/        # how it behaves today
└── changes/      # what is changing
    └── archive/  # finished, dated
  • Open source, works with 30+ agents
  • Plain Markdown you can read on GitHub
  • Skills for the agent, a CLI for you

The loop

Explore, propose,
apply, archive

  1. ExploreTalk options through. The agent writes nothing.
  2. ProposeProposal, spec, design and tasks in changes/. You edit them.
  3. ApplyIn a fresh chat, the agent follows tasks.md.
  4. ArchiveAfter you verify: the spec becomes the new truth.

Anatomy of a change

One folder
per change

proposal.md

Why, and what is in and out of scope.

specs/

What must be true: requirements and scenarios.

design.md

How: decisions and files touched. Optional.

tasks.md

The checklist the agent follows, each task with its check.

Writing specs

Requirements you
can check

## ADDED Requirements

### Requirement: Type filter
The gallery SHALL let the user show only Pokémon of one type.

#### Scenario: Pick a type
- GIVEN the gallery shows all Pokémon
- WHEN the user selects "Fire"
- THEN only Fire-type Pokémon are shown
- AND the URL contains ?type=fire
SHALL / MUST = mandatory. Every requirement gets a scenario; every THEN must be observable.
Practice

Make it
testable

“It should be fast”

Fast for whom, measured how?

“Nice error messages”

Which errors, what does the user see?

“Works on mobile”

Which widths, which interactions?

Pick three vague requirements from last year's student projects for this exercise.
Reviewing a proposal

Before you say
“apply”

  • The intent fits in two sentences
  • Out of scope is written down — agents love extras
  • Every scenario has a THEN you can see
  • One task = one commit
  • Nothing touches secrets or other people's data
After apply: review the diff against the scenarios, not against your memory of the chat.
When

Spec it,
or skip it?

Spec it

  • A new feature
  • An API or data model
  • Anything someone will rely on

Skip it

  • Typos and styling tweaks
  • Throwaway prototypes
  • You don't know yet what you want — explore first
